# Assumptions & Design Decisions

Where the brief left room for interpretation, this is what I chose and why.

## Data & money

1. **Amounts are decimal with 2 places** (e.g. rupees and paise). They're stored as `NUMERIC(18,2)`, never as floats. Amounts with more than 2 decimals are **rejected** rather than silently rounded, because rounding money behind the client's back is worse than a clear 400.
2. **Amounts must be JSON numbers.** `"10"` (a string) is rejected, so there's no implicit coercion.
3. **The maximum single amount is 1,000,000,000.** This is a sanity limit against typos and overflow, easy to change in `src/shared/validation.ts`.
4. **Single currency.** The brief doesn't mention currencies, so there's no currency field.
5. **Balances are returned as JSON numbers.** With 2 decimals and the limits above they're exact in IEEE-754 doubles. A multi-currency or high-value system would return strings instead.
6. **IDs are UUIDs (v4)** generated by the database. They're unguessable and unique without coordination.

## Accounts

7. **Only `name` is accepted when creating an account.** Sending `balance`, `id`, `created_at` or any other field returns `400` instead of being silently ignored, so a client that thinks it set a balance finds out straight away.
8. **Names are trimmed** and must be 1–255 characters. Names don't have to be unique, since two people can share a name.
9. **Accounts can't be deleted or renamed.** The brief has no such endpoints, and deleting an account with history would break the ledger (`ON DELETE RESTRICT`).

## Transactions

10. **The account comes from the URL** (`POST /api/accounts/{id}/transactions`), not the body. That's the RESTful shape for a sub-resource, and it means a body can't contradict the URL.
11. **`description` is optional** (stored as `null` when absent, max 255 characters). The brief lists it as a field but doesn't say it's required. `reference_id` *is* required, as the brief says.
12. **`reference_id` is an idempotency key per account.** It's trimmed, must be non-blank, and is at most 100 characters.
13. **A duplicate `reference_id` returns `409 Conflict`** with the *original* transaction in `error.details.existing_transaction`, even if the new payload differs (different amount or type). The retry is treated as a mistake, not a new transaction. A client can read the original from the response.
14. **Rejected transactions are not stored.** A debit refused for insufficient funds leaves no row, so its `reference_id` isn't consumed and the client can retry with the same reference once the account is funded. (The alternative, storing failed attempts, would need a status column, which the brief's "must not affect balance" wording doesn't ask for.)
15. **Insufficient balance returns `422 Unprocessable Entity`.** The request is well-formed but breaks a business rule. That keeps it apart from `400` (malformed input) and `409` (duplicate).
16. **The debit limit is the balance.** No overdraft, and debiting exactly to `0` is allowed.

## History

17. **Default `limit` is 20, maximum is 100.** Out-of-range values return `400` rather than being clamped, matching the brief's "invalid pagination parameters" error case.
18. **A page past the end returns `200` with an empty list** and correct `total_records`/`total_pages`. It's a valid question with an empty answer, not an error.
19. **Ordering is `created_at DESC, id DESC`.** `id` breaks ties so pages never overlap or skip rows. `created_at` uses `clock_timestamp()`, so a write that waited for a row lock still gets a later timestamp than the one it waited for.
20. **History for an unknown account returns `404`**, not an empty list, so a typo in the id is caught.

## Transfers (bonus)

21. **A transfer appears in both accounts' histories** as a normal debit and credit, linked by `transfer_id`, so balance = sum of transactions still holds for each account.
22. **The transfer's `reference_id` is unique per source account.** The debit leg reuses it on the source account. The credit leg gets `transfer:<transfer_id>` on the destination, so it can never collide with that account's own references.
23. **Transferring to the same account is rejected (`400`).**

## Scope

24. **No authentication or authorization.** The brief doesn't ask for it, and in production this API would sit behind an auth layer.
25. **Not-found and validation errors are checked before business rules.** For example, a transaction on a non-existent account with an invalid amount returns `400`, because the body is validated first.
26. **Database:** PostgreSQL. It has real ACID transactions, row locks and CHECK/UNIQUE constraints, and it's the same engine as Supabase. For zero-setup local runs, embedded PGlite (Postgres in WASM) is used when `DATABASE_URL` isn't set.
